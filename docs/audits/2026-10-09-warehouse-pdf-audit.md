## ความเสี่ยงในขั้นตอนสร้างและแชร์ PDF

1. API /api/delivery-pdf เปิดหน้าบิลใหม่และทำ PDF จากข้อมูลบิล ไม่มีด่านเทียบกับออเดอร์
2. share-delivery-pdf.ts:259–270 เมื่อ server PDF สำเร็จ อาจสร้าง previewImages จาก DOM หน้าเดิม
   มือถือเลือกแสดง previewImages ใน delivery-pdf-preview-modal.tsx:319
   จึงมีโอกาสเห็นภาพตัวอย่างจากข้อมูลเก่าขณะที่ไฟล์ที่จะส่งมาจากข้อมูลใหม่
   ยืนยันจากโค้ด แต่ไม่ได้จำลองการเปลี่ยนข้อมูลระหว่างสร้าง preview จริง
3. เมื่อ server PDF fail มี fallback ทำ PDF จาก DOM หน้าเดิมที่ share-delivery-pdf.ts:278
   ถ้าหน้าเปิดค้างก่อนแก้ออเดอร์ ไฟล์ fallback จึงมีความเสี่ยงใช้ข้อมูลค้าง
4. preview modal ถือ File เดิม; download/share ใช้ไฟล์นั้นโดยไม่ตรวจ revision ของออเดอร์ซ้ำ
   แก้ข้อมูลจากอีกหน้าหรืออีกอุปกรณ์หลังสร้าง preview แล้ว ยังส่ง File เก่าได้
5. uploadTempPdfAction เก็บไฟล์ชั่วคราวและมี cleanup ไฟล์อายุมากกว่า 24 ชั่วโมงเมื่ออัปโหลด
   ไม่มีตารางผูก PDF กับ order revision, ยอด, รายการ, hash และเหตุการณ์ส่งที่ตรวจย้อนกลับได้
   ไม่ได้ลบตรงเวลาครบ 24 ชั่วโมงเสมอ ขึ้นกับการ cleanup และ limit 100
6. PDF รวมเลขบิลที่ไม่มีแล้วไม่ถูกแก้ย้อนกลับ และไม่มีการเตือนเอกสารรุ่นเก่าในแชท
7. ไม่มีสิทธิ์หรือ connector แชทลูกค้าในการตรวจครั้งนี้; upload/เปิดตัวอย่างไม่เท่ากับส่งสำเร็จ

## วิธีตรวจย้อนหลังและทำงานวันนี้

- เก็บไฟล์ที่ส่งจริงหรือ export chat attachment พร้อมวันเวลาและร้าน
- เทียบเลขบิล วันที่ ร้าน SKU หน่วย จำนวน ราคาต่อหน่วย และยอดทุกรายการ
- แยกยอดสินค้าจากยอดค้าง/ผ่อน; อย่าเทียบ grand total กับยอดสินค้าโดยตรงเมื่อมีหนี้เก่า
- ถ้าคนละยอด ตรวจว่ามีการแก้หลัง export หรือไม่ และหาเอกสารรุ่นล่าสุดที่ลูกค้าได้รับ
- กรณีเจ๊แมว ตรวจว่าไฟล์ที่ส่งเป็น 34,740 หรือ 34,170 และส่งรุ่นใหม่ถ้าลูกค้ายังมีรุ่นเก่า
  รายงานนี้ไม่ได้ส่งอะไรหาลูกค้า
- ระหว่างยังไม่มีแพตช์ ให้แก้ให้เสร็จ ปิดหน้าตัวอย่างเก่า เปิดบิลใหม่ ตรวจสินค้ากับออเดอร์ สร้างไฟล์ใหม่แล้วส่ง
- ทุกการแก้หลังส่ง ต้องสร้างและส่งบิลใหม่ ระบุว่าฉบับใหม่แทนฉบับเดิม
- ตรวจความตรงกันทั้งสองคลังก่อนสรุปยอดรายวัน; รายการผิดต้องไม่ถูกปล่อยผ่านเพียงเพราะมี warning

## แนวแก้ถาวรที่เล็กแต่ครบ

1. บันทึกออเดอร์และบิลให้เป็น transaction เดียว หรือมีสถานะบังคับไม่ให้ export จน reconcile สำเร็จ
   คำนวณยอดหัวจากสินค้าที่บันทึกจริงและล็อก/ตรวจรุ่นเพื่อไม่ให้ payload เก่าทับข้อมูลใหม่
2. ก่อนสร้าง PDF ทุกช่องทาง ตรวจ order header = order item sum = delivery header = delivery item sum
   รวมทั้งจำนวน หน่วย ราคา SKU และชุดรายการ; ถ้าไม่ตรงหรืออ่านไม่สำเร็จ ให้หยุดสร้าง
   สร้างไฟล์จาก snapshot ที่ผ่านการตรวจเดียวกันทั้งเอกสาร ไม่อ่านหัวและสินค้าแยกช่วงจนได้คนละรุ่น
3. ภาพ preview และไฟล์แชร์ต้องมาจาก PDF เดียวกัน; fallback ห้ามข้ามการตรวจข้อมูลล่าสุด
4. ผูก PDF กับ order revision และตรวจอีกครั้งก่อนแชร์/ดาวน์โหลด
   หากแก้ภายหลัง export ให้ขึ้น “ต้องสร้างและส่งบิลใหม่” และไม่ให้แชร์ไฟล์เก่าจากในแอป
5. เก็บไฟล์ immutable พร้อมรายการ/ยอด ณ เวลา export, revision, hash, ผู้ทำรายการและเวลา
   เก็บประวัติการส่งแยกจากประวัติ export; manual share ต้องมีการยืนยัน ไม่อ้างว่าส่งสำเร็จจาก upload
   เอกสารลูกค้าควรใช้สิทธิ์เข้าถึงหรือลิงก์มีอายุ โดยเก็บสำเนาประวัติภายในเพื่อ audit
6. หน้าออเดอร์แสดงสถานะสั้น ๆ เช่น “บิลล่าสุดตรงแล้ว” / “แก้หลังส่ง ต้องส่งใหม่”
   และมีผลตรวจรายวันแยกรายคลังพร้อมร้านที่ต้องแก้ ไม่ใช้การเทียบยอดรวมรายวันอย่างเดียว
7. เมื่อปล่อยแพตช์ ทดสอบ 2,000→2,500, เพิ่ม/ลด/ลบสินค้า, เปลี่ยนราคา, บันทึกล้มเหลว,
   แก้พร้อมกัน, PDF เปิดค้าง, fallback และแก้หลัง export ทั้งกรุงเทพและต่างจังหวัด

ไม่รับประกันว่าไฟล์ที่ส่งออกไปอยู่นอกระบบจะอัปเดตหรือถูกเรียกคืนอัตโนมัติ
สิ่งที่ระบบควรรับประกันคือหยุดสร้าง/ส่งเอกสารค้างภายในแอป และตรวจพบเมื่อออเดอร์เปลี่ยนหลังส่ง
ยังไม่ได้ติดตั้งกลไกเหล่านี้ และไม่ได้สร้าง automation รายวันในการตรวจครั้งนี้
