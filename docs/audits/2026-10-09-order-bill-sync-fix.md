# การแก้ออเดอร์ บิลจัดส่ง และ PDF ให้ตรงกัน — 9 ตุลาคม 2569

## พฤติกรรมที่แก้

- การแก้สินค้าในหน้าออเดอร์บันทึกสินค้า ราคาประจำร้าน ยอดออเดอร์ และบิลจัดส่งในธุรกรรมเดียว ถ้าล้มเหลวจะย้อนกลับทั้งหมด
- ตรวจเวอร์ชันออเดอร์ก่อนบันทึก ป้องกันหน้าจอเก่าเขียนทับการแก้ไขล่าสุด
- ยอดหัวออเดอร์คำนวณจากสินค้าที่บันทึกจริงเสมอ ป้องกันการเพิ่มยอดก่อนบันทึกสินค้าสำเร็จ
- เพิ่มสินค้าเข้าออเดอร์เดิมด้วยการรวมและซิงก์บิลแบบ atomic; แยกสินค้าขายกับส่งชดเชย
- ฟังก์ชันสร้างบิลอ่านสินค้าปัจจุบันหลังล็อกกลุ่มร้าน/วันที่/คลัง ป้องกันข้อมูลจากหน้าจอเก่าทับบิลใหม่
- หน้าแก้จำนวนส่งจริงปรับจำนวนในออเดอร์และบิลตามกัน พร้อมคงการลดแบบสูญเสีย
- การพิมพ์รวมแยกคลัง หน่วยขาย และสินค้าส่งชดเชย ไม่รวมรายการต่างประเภทเข้าด้วยกัน
- ตรวจออเดอร์และบิลก่อน/หลังโหลดหน้าพิมพ์ และก่อน/หลังสร้าง PDF ใช้ไฟล์ PDF จริงเป็นพรีวิว
- PDF มีลายเซ็นผูกเวอร์ชันข้อมูลกับเนื้อไฟล์ ตรวจอีกครั้งก่อนอัปโหลด แชร์ คัดลอกลิงก์ และดาวน์โหลด
- ถ้าข้อมูลเปลี่ยน ต้องสร้าง PDF ใหม่; การสร้างบิล PDF ไม่ย้อนใช้ภาพหน้าจอเก่าเมื่อเซิร์ฟเวอร์ล้มเหลว
- รอหน้าบิลมองเห็นได้ก่อนสร้าง PDF เพื่อป้องกันไฟล์ว่างจากหน้าเว็บที่ยังโหลดข้อมูลไม่ครบ
- คงยอดผ่อนเดิมเมื่อพิมพ์ซ้ำโดยไม่ได้ระบุยอดผ่อนใหม่ และรายงานความล้มเหลวของการอัปเดตใบวางบิล

## ข้อมูลจริงที่แก้

แก้หัวออเดอร์เฮียสมนึก วันที่ 8 ตุลาคม เลข DN2026100376 จาก 2,745 เป็น 915 บาท ตามยอดสินค้าที่บันทึกจริงและบิลเดิม ไม่เพิ่มหรือลบสินค้าโดยคาดเดา

ตรวจหลังแก้เมื่อ 9 ตุลาคม ประมาณ 15:32 น.: บิล confirmed ทั้งหมด 1,262 บิล (กรุงเทพ 733, ต่างจังหวัด 529) ไม่พบความต่างของยอดหัวออเดอร์/บิล จำนวน ราคา หน่วยขาย และการเชื่อมสินค้า ระหว่างข้อมูลที่บันทึกอยู่

## การตรวจสอบ

- `npm run lint` และ `npm run build` ผ่าน
- ชุดทดสอบที่เกี่ยวข้อง 7 รายการผ่าน: สินค้าชดเชย การเรียกบันทึกแบบ atomic ลายเซ็น PDF ไฟล์ถูกเปลี่ยน ข้อมูลเก่า บิลหาย ข้ามองค์กร และ batch 200 บิล
- `supabase/tests/order_delivery_consistency.sql` ผ่านทั้งสองคลัง: เพิ่มจำนวน บันทึกล้มเหลวแล้ว rollback เวอร์ชันเก่า payload พิมพ์เก่า ยอดหัวออเดอร์ สต็อกสูญเสีย/คืนคลัง สินค้าส่งชดเชย และรักษายอดผ่อน ทุกการทดสอบ rollback ไม่ทิ้งออเดอร์หรือสต็อกทดสอบไว้
- สร้าง PDF ผ่าน endpoint จริงบน production build ในเครื่อง: ใบเดียว 1 หน้า; พิมพ์รวมและพรีวิวอย่างละ 2 หน้า ทั้งสองคลัง ยอด 390 และ 92,425 บาทตรงกับฐานข้อมูล ตรวจข้อความ ภาพ และ hash ของไฟล์แล้ว
- มีชุดทดสอบตัวอักษรเดิม 3 รายการที่ไม่ผ่านใน baseline ก่อนแพตช์นี้ ไม่ได้เปลี่ยนขนาดตัวอักษรเพื่อทำให้ assertion เหล่านั้นผ่าน
- การสร้าง types ผ่าน CLI ไม่สำเร็จเนื่องจาก access token ที่บันทึกไว้ใช้ไม่ได้ จึงสร้าง types จาก Supabase connector ของโปรเจกต์เดียวกัน

## ขอบเขตและข้อจำกัด

PDF ที่ดาวน์โหลดหรือส่งเข้าห้องแชทแล้วเป็นไฟล์คงที่ การแก้ออเดอร์ภายหลังไม่เปลี่ยนไฟล์ที่ลูกค้าได้รับ ต้องสร้างและส่งฉบับใหม่ ไม่มีหลักฐานการส่งในแชทลูกค้าให้ตรวจว่าลูกค้าได้รับเวอร์ชันไหน และยังไม่ได้ทดสอบการแชร์บน iPhone/LINE จริง

ไม่สร้างระบบแชทอัตโนมัติหรือเปลี่ยนรูปแบบตัวอักษรบิล ชุดบิลที่ token ใหญ่เกิน 7,000 ตัวอักษรจะให้แบ่งสร้าง PDF เป็นชุดเล็กลง

การตรวจ Supabase security advisors ไม่พบรายการเกี่ยวกับฟังก์ชันใหม่ของแพตช์นี้ ฟังก์ชันใหม่และตัวสร้างบิลที่แก้ให้ใช้เฉพาะ service role เท่านั้น มีคำเตือนด้านความปลอดภัยเดิมอยู่นอกขอบเขตงาน เช่นฟังก์ชันอื่นที่เปิดให้ anon เรียกได้ และ security-definer views:
[คู่มือฟังก์ชันที่เปิดเรียกโดยไม่เข้าสู่ระบบ](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable),
[คู่มือ security-definer views](https://supabase.com/docs/guides/database/database-linter?lint=0010_security_definer_view)
