# Fresh reserve activity

The latest activity panel reads `fresh_reserve_activity`, scoped to the signed-in organization and selected order date. Database triggers record effective Bangkok fresh demand for ANP180–ANP182 after factory production has been confirmed. Order item edits, cancellation/deletion, delivery routing, customer defaults and special quantities are covered. Changes in the same transaction and source are combined; zero net changes are removed. Customer default changes aggregate all affected orders once per date/product.

`demand_change` is the change in factory demand. Positive `reserve_change` is reserve actually consumed; negative means returned. Consumption is clipped at available production capacity, so shortages appear separately. `available_after` is the balance at that event, not today's latest balance. The main table continues to calculate the current balance from confirmed production and current demand.

Existing edited items were preserved with `reason=legacy` and unknown before/delta/balance values; the UI says “ไม่มีข้อมูลก่อนแก้”. They cannot establish historical reserve consumption. New history begins with migration `20261009113550`; refinement `20261009113951` prevents customer-default changes and delivery synchronization from duplicating or mislabeling events. The ledger is inaccessible to anonymous/authenticated API roles; the server queries it after role authorization.

Verification: `node scripts/verify-fresh-reserve-activity.mjs` runs disposable local PostgreSQL scenarios on port 55439 and rolls all changes back. `node --experimental-strip-types scripts/verify-fresh-reserve-copy.mjs` checks user-facing labels. `node scripts/verify-fresh-reserve-ui.mjs [origin]` checks desktop/mobile and blocks all save requests. Production rollback verification reduced an existing 15 kg item to 10 kg, asserted a 5 kg return/balance, restored it and asserted zero activity, then rolled back the transaction. October 9 balances remained 45 / 10 / 0 kg.
